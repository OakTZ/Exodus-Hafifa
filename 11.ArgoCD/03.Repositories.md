### Goals
- The trainee will know which kinds of repositories ArgoCD can deploy from
- The trainee will know how to connect public and private repositories to ArgoCD, declaratively
- The trainee will understand how to organize Git repositories for GitOps

### Tasks
- **Repository types** - read about the repository types ArgoCD supports and explain when you would use each one:
  - Git repository (HTTPS and SSH)
  - Helm chart repository (a classic `index.yaml` based repo)
  - OCI registry (Helm charts stored as OCI artifacts)
- In an Application that uses a Helm repository, what does `targetRevision` mean? And what does it mean for a Git repository?
- Why is pointing `targetRevision` at `HEAD` or a branch different from pointing it at a tag or a commit SHA? When would you choose each one?
- **Connecting repositories**:
  - Connect a repository with the CLI (`argocd repo add`), then find the Kubernetes resource ArgoCD created for it
  - What label marks a Secret as a repository for ArgoCD?
  - What is a **credential template** (`repo-creds`)? What problem does it solve when you have 30 repositories on the same GitLab group?
  - Why is it better to define repositories declaratively than with the CLI or UI?
  - The repository Secret contains a password or token. How would you store it in Git without leaking it? (Read briefly about Sealed Secrets and External Secrets Operator)
- **Organizing repositories**:
  - What is the difference between an **application (source code) repo** and a **config / GitOps repo**? Why do most teams keep them separate?
  - Compare a single GitOps monorepo with a repo per team or per environment. What are the pros and cons?
  - Compare a **folder per environment** (`envs/dev`, `envs/prod`) with a **branch per environment**. Why is branch-per-environment usually considered an anti-pattern?
  - How does a new image version get from the CI pipeline into the GitOps repo? (Read briefly about ArgoCD Image Updater)
