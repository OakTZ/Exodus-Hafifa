# 🚀 ArgoCD Exercise

🕒 **Estimated Time**: 2 days
🧪 **Kubernetes Cluster Type**: `minikube` (or `kind`)

In this exercise you will take the Helm charts you wrote in the 10.Helm DevOps exercise (the **NGINX** web server and the **caller** microservice) and stop deploying them by hand. By the end, a single `kubectl apply` will bring up the whole environment from Git.

> **Important notice!**
> From Part 4 on, you are not allowed to run `helm install/upgrade` or `kubectl apply/edit/delete` on your workloads. Every change goes through Git.
> The only exceptions are installing ArgoCD itself, the bootstrap step, and the places where the exercise asks you to break things on purpose.

## Prerequisites
- A running minikube cluster
- The `nginx` and `caller` Helm charts from the 10.Helm DevOps exercise
- A **private** Git repository that ArgoCD can reach. Either:
  - A private project on GitLab (you created an account in 02.Git), or
  - **Gitea** installed on your minikube with Helm, like in the Helm exercise

Use the following layout for your GitOps repository (you may change it, but be ready to explain why):
```
hafifa-gitops/
├── bootstrap/
│   └── root.yaml            # the ONLY file you apply by hand
├── argocd/                  # everything the root app manages
│   ├── projects/
│   └── apps/
├── charts/
│   ├── nginx/
│   └── caller/
└── envs/
    ├── dev/
    └── prod/
```

## 1. Install ArgoCD
1. Install ArgoCD with the official Helm chart into the `argocd` namespace. Keep your `values.yaml` in the repo, because you will need it again.
2. Access the UI with `kubectl port-forward` and log in with the `argocd` CLI.
3. Change the admin password and delete the initial admin secret.
> **Check:** `argocd version` shows both the client and the server versions.

## 2. Repositories
1. Connect your private GitOps repository **declaratively**, with a Kubernetes Secret.
   - Use a credential template (`repo-creds`) for your GitLab group / Gitea organization instead of a credential for a single repo.
   - Do **not** commit the token in plain text. Apply this Secret by hand (and write down that you did), or use Sealed Secrets for the bonus.
2. Connect the public **podinfo** Helm repository: `https://stefanprodan.github.io/podinfo`
3. **Bonus:** podinfo is also published as an OCI artifact in `ghcr.io/stefanprodan/charts`. Find out how to register an OCI Helm repository and use it instead.
> **Check:** `argocd repo list` shows all repositories with status `Successful`.

## 3. Project
Create an AppProject named `hafifa`:
- `sourceRepos`: only your GitOps repo and the podinfo repo
- `destinations`: only the in-cluster server, and only namespaces matching `hafifa-*`
- Cluster-scoped resources: block everything except `Namespace`
- Add a project role `read-only` that can only `get` applications in the project

Save it under `argocd/projects/`. For now, apply it by hand.
> **Check:** Create an Application in the `hafifa` project that deploys to `kube-system`. It must fail. Copy the error and explain it.

## 4. Applications
1. Create an Application `nginx-dev` in the `hafifa` project:
   - Source: `charts/nginx` from your GitOps repo, with the values file `envs/dev/nginx-values.yaml`
   - Destination: namespace `hafifa-dev` (let ArgoCD create it)
   - Sync policy: **manual**
2. Sync it from the UI, then look at the resource tree. Which resources did ArgoCD create? Is the release in `helm list -A`?
3. Change the HTML page (the ConfigMap) in Git and push. Watch the Application go `OutOfSync`, look at the **diff**, then sync.
4. Change the sync policy to **automated**, with `prune` and `selfHeal`. Then:
   - `kubectl scale` the NGINX Deployment to 5 replicas. What happens? How long does it take?
   - Delete a template (e.g. a test ConfigMap you added) from the chart in Git. What happens to the resource in the cluster?
   - Push a broken change (e.g. an image tag that doesn't exist). What do the sync status and the health status show?
   - Roll back the broken change the GitOps way.
5. Create an Application `caller-dev` the same way.
6. Create an Application `podinfo-dev` that uses **multiple sources**: the chart from the podinfo Helm repo, and a values file from your GitOps repo (`envs/dev/podinfo-values.yaml`). Pin the chart version.

Save all the Applications under `argocd/apps/`.

## 5. App of Apps
1. Write `bootstrap/root.yaml`, an Application that syncs the `argocd/` directory (recursively) with auto-sync.
2. Make sure the AppProject is created before the Applications that use it (hint: sync waves).
3. Add the cascade-delete finalizer to the child Applications.
4. **Disaster recovery drill:** delete your minikube, then bring everything back using only:
   - `helm install` of ArgoCD with your saved values
   - the repository Secret
   - `kubectl apply -f bootstrap/root.yaml`
> **Check:** Everything comes back, without any other manual step.

## 6. ApplicationSet
Writing an Application per app per environment doesn't scale. Replace the `nginx-*`, `caller-*` and `podinfo-*` Applications with **one** ApplicationSet:
- Use a **Matrix** generator that combines:
  - a **Git directory** generator over `envs/*`
  - a **List** generator of apps: `nginx`, `caller`, `podinfo` (hint: the list items can carry fields, e.g. which source to use)
- Use `goTemplate: true`
- Generate Applications named `<app>-<env>` that deploy to namespace `hafifa-<env>`
- The root app should now deploy the ApplicationSet instead of the individual Applications

Then:
1. Add `envs/prod` with different values (e.g. 3 replicas and a different page). The prod apps should appear without editing the ApplicationSet.
2. Add `envs/staging`, wait for it to deploy, then delete the folder. What happened to the Applications and to the running pods? Set `preserveResourcesOnDeletion` and repeat. What changed?
> **Check:** `argocd app list` shows 6 Applications (3 apps x 2 envs), all `Synced` and `Healthy`.

## 7. Sync Waves and Hooks
### Inside an Application
In the `nginx` chart:
1. Make sure the ConfigMap and the Secret are applied in an earlier wave than the Deployment.
2. Add a `PreSync` hook Job that prints the Git revision being deployed (hint: pass it in from the values or the app's environment).
3. Add a `PostSync` hook Job (a **smoke test**) that `curl`s the NGINX Service and fails if the page doesn't contain the expected text.
4. Add a `SyncFail` hook Job that prints a "deployment failed" message.
5. Choose the right hook delete policy for each Job and explain why.
6. Push a change that breaks the page on purpose. Show that the smoke test fails, the `SyncFail` hook runs, and the Application shows the failure.

### Between Applications
The caller is useless until NGINX is up, and podinfo should come up first, before both of them.
1. Generated Applications can't use sync waves between them. Pull `podinfo` out of the ApplicationSet into its own Application under `argocd/apps/`, with a wave that is earlier than the ApplicationSet.
2. Push a broken podinfo image tag. Does the root app wait for podinfo before it creates the ApplicationSet? Why not?
3. Fix it by adding a health check for `argoproj.io/Application` resources to `argocd-cm`, through your ArgoCD Helm values. Repeat step 2 and show that the root app now stops at the podinfo wave.
4. **Bonus:** use **Progressive Sync** (`RollingSync`) on the ApplicationSet so `dev` is synced and healthy before `prod` starts.

## 🏁 Bonus
- Let ArgoCD manage **itself**: add an Application for the ArgoCD Helm chart under `argocd/apps/`. What can go wrong?
- Store the repository Secret in Git with **Sealed Secrets** (deployed by ArgoCD, of course)
- Configure a **webhook** from your Git server to ArgoCD so syncs start immediately after a push
- Add a **sync window** to the `hafifa` project that denies syncs to `hafifa-prod` on weekends
