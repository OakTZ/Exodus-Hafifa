### Goals
- The trainee will understand what ArgoCD is and how it works internally
- The trainee will know the ArgoCD components and the responsibility of each one
- The trainee will understand the difference between sync status and health status

### Tasks
- Install ArgoCD on your minikube using the official Helm chart (`argo/argo-cd`) into the `argocd` namespace
- Access the UI using `kubectl port-forward`, and log in with the CLI (`argocd login`)
  - Where does the initial admin password come from? Why should you delete it after you change it?
- Run `kubectl get pods,deploy,sts -n argocd` and explain the role of each component:
  - `argocd-server`
  - `argocd-repo-server`
  - `argocd-application-controller` (why is it a StatefulSet and not a Deployment?)
  - `argocd-applicationset-controller`
  - `argocd-redis`
  - `argocd-dex-server`
  - `argocd-notifications-controller`
- Which component clones your Git repository and renders Helm charts? Which one talks to the Kubernetes API to apply resources?
- ArgoCD stores its configuration as Kubernetes resources. List the CRDs ArgoCD installed (`kubectl get crd | grep argoproj`)
- Explain the **reconciliation loop**:
  - How often does ArgoCD check Git by default? How can you make it react to a push immediately?
  - What does ArgoCD compare to decide that an Application is out of sync?
- Explain the difference between **Sync Status** (`Synced`, `OutOfSync`) and **Health Status** (`Healthy`, `Progressing`, `Degraded`, `Suspended`, `Missing`, `Unknown`)
  - Can an Application be `Synced` and `Degraded` at the same time? Give an example
  - How does ArgoCD decide that a Deployment is healthy? What about a CRD it doesn't know?
- What do the `argocd-cm` and `argocd-rbac-cm` ConfigMaps configure?
- Does ArgoCD run `helm install`? How can you check (hint: `helm list -A`)? What are the consequences?
